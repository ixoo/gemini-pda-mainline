## Observations

1. Vendor patch `0013` declares and calls
   `mt6797_dvfsp_vendor_coordinator_vendor_probe()` and
   `mt6797_dvfsp_vendor_coordinator_vendor_remove()` from the vendor cpufreq
   probe/remove lifecycle.
2. No patch in the 15-entry vendor experiment series defines either symbol.
   Their implementations exist in the separate Linux 7.1 patch `0269`.
3. Vendor patch `0015` makes provenance observation require a bound lifecycle
   and `mainline_registered=true`; it cannot publish a successful table epoch
   or calibration handle through the stock Gemian runtime by itself.
4. The Buildbox vendor receipt compiled five affected objects against prepared
   Linux 7.1 headers. It did not perform a final vendor-kernel link, construct a
   boot image, or mark the output as a boot candidate. The temporary checkout
   and objects were removed as recorded.
5. The 2026-08-14 bounded SSH census of the running stock Gemian kernel found
   no epoch, generation, calibration handle, owner, transition, or shared-lock
   publication surface.

## Decision

The cross-tree object-compile gate is valid, but it is not a runnable runtime
candidate. A repeated census of the unchanged stock Gemian kernel cannot close
the missing provenance gate. Before another device boot, the project needs a
separately reviewed, default-off observation candidate that:

- links the exact coordinator implementations and vendor call sites in one
  kernel image and proves the final link has no unresolved experiment symbols;
- publishes only a bounded read-only provenance record after lifecycle binding;
- requires nonzero variant, mutable table epoch, calibration handle, source
  generation, owner handle, and transition handle from one locked snapshot;
- exposes explicit invalidated/unavailable states and refuses stale identity;
- registers no regulator provider, replaces no vendor setter, performs no
  experiment-triggered hardware write, and leaves CPU8/CPU9 admission closed;
- passes a full Buildbox kernel link and boot-container review before it can be
  considered for guarded logical-boot2 deployment.
