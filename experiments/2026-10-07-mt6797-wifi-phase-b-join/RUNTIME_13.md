## Diagnosis, from the pinned source and the pinned binary

The join script started the supplicant with `-f <log>`. In wpa_supplicant 2.11
`main.c` the option string carries `f:` unconditionally, but `case 'f'` exists
only under `CONFIG_DEBUG_FILE`; without it the option falls to `default:`,
which prints the usage text and exits 0. The pinned static build's
[configuration](helper/wpa_supplicant.config) has no `CONFIG_DEBUG_FILE`, so
the supplicant never initialised, never scanned, and never created the log.
The pinned binary (`0487b710…`) reproduces this under QEMU user emulation on
Buildbox-1: with `-Dnl80211 -iwlan0 -c <conf> -f <log> -d` it prints 1593
bytes containing `usage:` and exits 0 without creating the log; `-h` lists no
`-f`; with the same arguments minus `-f` and stdout and stderr redirected it
initialises (`Successfully initialized wpa_supplicant`, `Initializing
interface 'wlan0'`), reads the configuration and proceeds to the nl80211
driver, failing only for the absent interface on the build host (exit 255, no
usage text), with its whole debug stream in the redirected file.

## Decision

The next boot is not an identical repeat: the join script now runs the
supplicant without `-f` and redirects its stdout and stderr into the private
RAM log under the script's `umask 077` (mode 0600), the same `-d` and no `-K`;
the export and its confinement are unchanged, and the log now exists whenever
the supplicant started. See [RUNTIME_14_PREPARATION](RUNTIME_14_PREPARATION.md).
Candidate 13 and its installed boot2 are reused unchanged; only the private
bound script changes, regenerated by the custodian from the corrected source.
