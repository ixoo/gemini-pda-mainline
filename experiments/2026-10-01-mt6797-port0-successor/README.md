# Inspect one queued port-0 successor

The [last authenticated mainline boot](../2026-10-01-mt6797-port0-header/results/runtime-1.json) read one 89-byte firmware debug event. Its post-read WRPLR reported another 80-byte port-0 packet, but that boot did not consume it. The next observation is whether a bounded PIO read can complete that queued packet and identify its header. This is needed to design event handling before normal commands and packet delivery; it is not a radio or network-interface test.

[Patch 0063](../../patches/proposals/0063-wifi-mediatek-inspect-one-port0-successor.patch) appends one call to the [bounded PIO receive path](../2026-10-01-mt6797-pio-rx/README.md) after the existing guarded first read. It calls only when that read succeeds and its full post-read WRPLR is exactly `0x00000050`. A new one-second deadline bounds the successor, whose caller buffer holds at most 80 bytes. The log contains status, transfer counts, WRPLR and complete header metadata; for a complete software event it also contains event ID and sequence. The packet body remains private and is wiped from the stack. No loop, retry, RF command, AP-DMA action or interface registration is added. The owner and failed-session lifetime remain retained as in the predecessor.

Before any physical boot, freeze and verify the exact kernel, DTB, initramfs, image, boot2 predecessor and recovery route. This candidate's unique observation is the successor read after the previous `89 -> 80` transition. One boot may issue at most one WLAN START, one capability query, one 89-byte first-event read and one successor read. If the prerequisite differs, the successor is skipped; preserve the log and investigate without replay. If the read completes as another debug event, design a bounded event drain before commands. If it is another event or packet type, map its source contract before handling it. Any malformed, partial or timed-out read poisons the HIF session; preserve evidence and stop without retry. A successful header does not establish calibration, regulatory policy, association or usable Wi-Fi.

The [preflight](results/preflight.json) records exact source and patch checks. The [Buildbox package](results/build.json) and [offline candidate](results/candidate.json) are validated for this boot. The candidate changes the kernel and the RAM root's release gate while retaining the previously booted board DT and firmware. Its parent is the boot2 image from the authenticated port-0 header session. The device's reviewed boot2 guard, full-partition checksum/readback, clean shutdown, owner physical selection, authenticated mainline collection and changed-boot Gemian return are required.

The first [USB watch](results/watch-1.json) expired at the MediaTek `20ff` stage after the boot2 write and verified readback. It saw no mainline route and issued no device SSH command. Physical boot2 selection and screen state were unconfirmed at that point, so the watch alone did not establish whether the candidate kernel ran. No second watch was started.

## Confirmed boot2 session

The owner subsequently confirmed physical boot2 selection with the console on. The expected USB gadget route appeared, and the installed candidate booted as `81c300e2-bcd1-4faf-a0b9-48fd9cdaa8a9`. The [runtime receipt](results/runtime-1.json) pins the complete private log and authenticated return. One WMT setup, firmware START and capability query succeeded. The first port-0 read reproduced the 89-byte debug event and its 80-byte successor; the bounded second read completed that 80-byte packet as another `0xe000` debug event, ID `0x27`, sequence 0. Its post-read WRPLR was zero. This establishes two complete packet headers in one boot, not general event handling or a future empty queue guarantee. Neither event body was published.

The A53 RAM-service regression passed, and reviewed recovery confirmed a changed Gemian boot with `wlan0` carrier. No mainline normal configuration, calibration application, radio command, packet DMA, network interface, scan, association or traffic was exercised. The next implementation must own asynchronous event handling and the ordered normal-command/configuration lifecycle before claiming usable Wi-Fi; the completed one-shot budget is not a repeat candidate.
