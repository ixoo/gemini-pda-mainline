# Bounded boot debug drain and private record preparation

The [authenticated successor boot](../2026-10-01-mt6797-port0-successor/results/runtime-1.json) received two complete port-0 debug events (`0xe000`, ID `0x27`) after capability, then reported an empty WRPLR. Those event bodies are private. [Patch 0064](../../patches/proposals/0064-wifi-mediatek-drain-bounded-boot-debug-events.patch) replaces the two hard-coded reads with a bounded drain: at most eight complete events under one one-second deadline, stopping on any other packet, port-1 pending length, malformed read or budget exhaustion. It logs only status, count and WRPLR.

[Patch 0065](../../patches/proposals/0065-wifi-mediatek-probe-private-record-preparation.patch) then calls the existing firmware-class record provider once. It reports only whether the complete local `WIFI.storage` record passed the selected format checks, and immediately releases the buffer. The runtime input is the privately retained, independently matched file from the [calibration applicability audit](../2026-09-05-mt6797-wifi-contract/CALIBRATION_APPLICABILITY.md#live-record-identity-follow-up--2026-10-01); neither its bytes, hash, address nor branch values belong in Git. These patches send no normal configuration, calibration or RF command, start no packet DMA and register no network interface. Provider success would prove only live lookup and format preparation, not firmware application or usable Wi-Fi.

One reviewed boot may perform at most one WMT setup, one WLAN START, one capability query, eight port-0 debug reads and one passive record preparation. Its distinct observation is whether the known debug queue can be drained and the firmware-class provider can read the matched private record. A non-debug packet, port-1 pending length, transfer error or absent/invalid record stops the one-shot session for private diagnosis; do not repeat the same artifact without a decision-changing measurement. The candidate must be built from a clean pushed commit, include only the authenticated private record as an additional RAM-root member, retain the proven board DT and firmware, and pass exact offline package, partition and recovery preflights. After a successful observation, the next step is to implement the selected ordered normal commands with a cfg80211 regulatory owner before any RF operation.

The [preflight](results/preflight.json) and [clean Buildbox package](results/build.json) passed; the [offline candidate](results/candidate.json) is checksum-bound and has not been installed. The private RAM root was generated by [the pinned retargeter](retarget-initramfs.py), and [the candidate composer](build-candidate.py) verified that its only changes were the release gate and one mode-0600 board-record member. The record payload stays in ignored local artifacts.
