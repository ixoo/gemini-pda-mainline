## Question or hypothesis

Can three default-off logical patches implement the audit-selected nested P30
finalizer and exactly one injected owner publication while leaving all physical
sources, production replay authority, hardware effects, and CPU requests
absent?

The positive result requires one P30-lock-spanning non-sleeping callback, exact
owner revalidation, a fully prepared scalar destination, health publication
last, and repeat rejection before the source callback.

## Safety assessment

This phase is hardware-free. It adds no production caller, physical reader,
production replay source, DT enablement, MMIO, SMC, I2C transaction, provider
operation, P30 prepare, CPU_ON, CPU_OFF, boot artifact, device access, or
partition write.

Only injected KUnit may exercise the publication function. The CPU-up gate
must remain `-EOPNOTSUPP` after injected publication, the MT6797 CPU boot
method must remain `-EAGAIN`, and CPU disable must remain false. No boot
candidate is defined.

## Observations

The definition pins three logical patches: a P30 nested finalizer, an atomic
default-off publisher, and injected tests. The test fixture contains eight
cases covering finalizer success and failure, exact publication and repeat,
replay rejection, source rejection, topology rejection, P30 collision, and a
final-owner mismatch.

The first submitted definition, commit `c697f934`, failed closed before any
source phase was committed. The semantic validator checks the unchanged
MT6797 PSCI boot and disable vetoes, but the bounded generation workspace had
not copied that read-only source file. The corrected definition pins and
copies its exact hash; the file remains outside every generated patch.

Commit `8a8d88e9` then failed the exact-file gate because the recorded value was
the adjacent generic arm64 `psci.c` hash rather than the MT6797-specific
`mt6797_psci.c` hash. The source-state and integrity markers remained exact.
The definition now pins the correct MT6797 veto file identity `7e332979…`.

Commit `21953be6` passed the finalizer and publisher semantic phases, then the
test validator rejected its own Kconfig query because it searched for the C
preprocessor form `CONFIG_ARM64_…` instead of the Kconfig declaration form
`config ARM64_…`. No patch package was emitted; only that validator spelling
changed for the retry.

Commit `3204c187` passed all three cumulative semantic validators, patch
separation, and exact replay. Strict checkpatch then rejected three finalizer
declarations ending in `(`. The retry changes only emitted C wrapping and the
matching validator anchors; all decision and effect boundaries are unchanged.

Commit `b9cb931b` removed those line-ending checks; strict checkpatch then
required the second argument in the same three declarations to align under the
opening parenthesis. Every semantic and replay gate still passed. The next
retry changes only that continuation alignment.

No kernel has been compiled, no generated patch has been admitted, and no
QEMU or device action has occurred.

## Analysis

The finalizer clears the logical claim only while retaining the private P30
raw lock, then invokes one callback that may take only `a72_state_lock`. This
prevents `prepare()` from entering before the callback returns and removes a
fallible release after a successful owner commit.

The publisher retains CPU-hotplug and transition ownership across locked
direct capture, A34 evaluation, P30 claim, and finalization. It has no
production caller. Its final callback byte-compares the pristine owner,
prepares every scalar before mutation, clears only the diagnostic A34 blocker,
and writes `AVAILABLE` last.
