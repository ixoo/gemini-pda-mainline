Findings
--------

1. The current expected-target validator is correctly after
   cpuinfo_store_cpu(), but check_local_cpu_capabilities() runs first. Its
   check_early_cpu_features() calls verify_cpu_asid_bits() and then verifies
   every boot-scope capability. A smaller ASID width calls cpu_panic_kernel().
   A strict boot-capability conflict does the same. The boot CPU converts the
   resulting CPU_PANIC_KERNEL status into a kernel panic. The later expectation
   validator therefore cannot protect serviceability from either mismatch.

2. The address-space gates are not all missing owners. Before enabling the
   target MMU, __enable_mmu checks the configured translation granule and parks
   the target with CPU_STUCK_REASON_NO_GRAN. When the finalized system uses
   52-bit VA, __cpu_secondary_check52bitva checks the required LPA2/VA field and
   parks with CPU_STUCK_REASON_52_BIT_VA. The exact profile uses 4 KiB pages,
   VA_BITS_52, and LPA2, so these linked assembly gates own the granule and VA
   failure paths. They do not panic or continue ordinary secondary startup.

3. ASID width still needs an earlier target-scoped owner. The existing
   get_cpu_asid_bits() and initialized system asid_bits contain the complete
   compatibility predicate: target width must be at least the system width.
   A non-mutating arm64 helper can evaluate that predicate before
   check_local_cpu_capabilities(). A failure must set CPU_STUCK_IN_KERNEL and
   park only the target; the standard verifier remains unchanged and repeats
   the check after a successful preflight.

4. Strict boot capabilities need the same ordering repair. The architecture
   already has one canonical descriptor table and exact optional/permitted
   conflict semantics. A target-scoped preflight can iterate every linked
   boot-scope descriptor, evaluate its local match, compare it with the frozen
   system bit, and return an error for exactly the conflicts that the standard
   verifier would panic on. It must not call cpu_enable(), update any system
   capability, or replace the standard verifier. This covers current and
   future compiled strict descriptors without a fragile MT6797 list, including
   GICv3 usability, VHE, MTE, and the unmeasured GICv5 PFR2 field.

5. The two remaining early-local GIC/hyp capabilities do not require invented
   target observations when their early-system bits are absent.
   ARM64_HAS_GICV5_LEGACY and ARM64_HAS_ICH_HCR_EL2_TDIR are explicitly
   PERMITTED_FOR_LATE_CPU: a target may have either while an early system that
   lacks it leaves it unused. The current-system producer must canonically
   record those two early-system bits. An absent bit permits a conservative
   ABSENT target plan; a present bit remains unresolved because the expected
   pair lacks the required target controller state.

6. The exact expected PFR0 has CSV2 zero and expected PFR1 has SSBS zero.
   Unknown target WA1 and WA2 outcomes can therefore be removed as planning
   dependencies by choosing the worst state: classify Spectre-v2 and
   Spectre-v4 present and commit VULNERABLE with no firmware conduit or
   callback. update_mitigation_state() only objects when a late CPU would make
   the system worse; a precommitted VULNERABLE state cannot be worsened by the
   target's later current result. A stronger current result may install a
   local mitigation but cannot invalidate the conservative receipt.

7. With the conservative Spectre-v2 state already VULNERABLE, the existing BHB
   policy deliberately applies no independent BHB mitigation. The BHB result
   is therefore VULNERABLE with no method; it does not consume the unmeasured
   CLRBHB field or WA3. If a later slice proves a mitigated v2 target, the exact
   Cortex-A72 k=8 software loop is the conservative fallback before WA3, but
   that stronger branch is not needed for the first closed contract.

8. The 23 unavailable modern register-image fields remain unavailable. Slice
   6 already omits every HWCAP whose target field is missing. The standard
   current-target ELF-HWCAP verifier runs before cpuinfo_store_cpu() and parks
   a target that lacks any final advertised HWCAP. No zero-filled expected
   field, coarse ID_REGS_VALID claim, or new prior-cycle measurement is needed.

Decision
--------

classification=confirmed-conservative-contract-with-preflight-ordering-gap

The remaining boundary does not require another device measurement. It needs
two source-only slices before expected-pair activation:

1. Add an architecture-owned late-target preflight before
   check_local_cpu_capabilities(). It must reuse the complete linked boot-scope
   descriptor set and the existing ASID-width owner, return without action for
   non-target or non-READY CPUs, park a mismatching target, and leave the
   standard checks unchanged. The existing assembly granule and VA gates stay
   unchanged.
2. Move GIC/hyp planning to canonical current-system early-cap bits and move
   Spectre-v2/v4/BHB planning and effects to the field-valid expected pair plus
   the conservative worst-case policy above. Unavailable modern IDs remain
   omissions. Keep a present early GIC/hyp state unresolved.

Only after both slices pass exact generation, rejecting mutations, enabled
Buildbox linkage, section, stack, call-order, and diagnostic inspection may a
separate slice activate the named-device expected pair and reassess the exact
remaining blocker mask. That later reassessment is still not a CPU request or
device candidate.

Required logical-slice-7 gates
------------------------------

- exact post-0430 source hashes and deterministic Buildbox generation;
- a generic boot-scope descriptor walk, not an MT6797 capability allowlist;
- a non-mutating ASID comparison against the initialized system width;
- READY and target-membership gating before any preflight result applies;
- preflight call order before check_local_cpu_capabilities(), with the existing
  standard check, cpu_postboot, cpuinfo storage, and full expectation validator
  retained in their current order;
- target-only CPU_STUCK_IN_KERNEL parking on mismatch, with no kernel panic,
  CPU_OFF, retry, online continuation, or state mutation;
- rejecting mutations for skipped descriptors, changed conflict semantics,
  cpu_enable calls, moved ordering, non-target application, fail-open return,
  weakened READY gating, altered assembly granule/VA gates, expected-pair
  activation, READY publication, or a CPU request;
- strict checkpatch, deterministic replay, canonical-series validation for all
  manifest profiles, and exact enabled-profile Buildbox compile before any
  later blocker or activation decision.
