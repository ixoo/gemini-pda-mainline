Hypothesis and unique observation
---------------------------------

The rejected predecessor reached a fatal NULL-pointer dereference at
14.121403 seconds before either pair terminal. It did not retain PC/LR, a call
trace, or the scheduler phase in progress. This child changes observation only:
it adds durable pre/post records around every existing task and parent phase.
The synchronization protocol, deterministic workload, timeouts, startup,
power, CPU_OFF prohibition, watchdog, and recovery sources are unchanged.

The decision-changing evidence is the last complete ordered phase record and
any following unmatched before record in attributable changed-cycle pstore.
Changed-cycle pstore is primary. The read-only USB/netcat stream is secondary
corroboration and may preserve a prefix, but cannot replace boot-ID continuity
or recovery evidence. Screen color or an automatic restart alone is not
classifying evidence.

Marker contract
---------------

Every record begins with `gemini-a72-sc-phase`. Parent records have no CPU
field. Task records require `cpu=8` or `cpu=9`.

The successful parent path has this order, with before/after around each item
except the final run-exit record:

  create8
  create9
  wake8
  wake9
  ready8-wait
  ready9-wait
  release
  done8-wait
  done9-wait
  stop8
  stop9
  run-exit

Each CPU independently has this task order, with before/after around every
item:

  task-ready
  task-start-wait
  task-work
  task-done

The complete successful path therefore has 23 parent records and eight task
records for each CPU, or 39 runtime records from 31 unique source strings.
CPU8 and CPU9 task records may interleave in either scheduler-valid order; no
global CPU8-versus-CPU9 order may be inferred.

PASS-only cross-causal requirements:

- wake-before for a CPU precedes that task's first record;
- both task-ready-before records precede release-before;
- release-before precedes either task-start-wait-after;
- task-done-before precedes that CPU's parent done-wait-after;
- task-done-after precedes that CPU's stop-after; and
- run-exit follows every executed stop-after record.

Every trace known continuous from create8-before, including a fault trace, must
retain a prefix of one reachable parent source path, each emitted task stream
as an exact prefix, task-done-after before its emitted stop-after, and run-exit
after every emitted stop-after. The stronger list above applies only to PASS
or when the corresponding pair-v7 wait field independently reports success. A
readiness or done timeout can legitimately let release or a parent wait-after
precede a late task record. Head-truncated pstore is handled as evidence loss
below and cannot be tested as a complete prefix.

A create failure can skip wake, ready, release, and done phases before bounded
cleanup. `kthread_stop()` can terminate the one successfully created but
never-woken kernel task without invoking its thread function, so no task marker
is required between stop-before and stop-after. Any emitted task marker
requires the corresponding explicit wake-before. The other CPU may have no
task or stop records. Such a branch requires corroborating create-after,
stop/run-exit, and pair-v7 fault fields; it is not a complete-path order error.

Observation sequence
--------------------

1. In ordinary Gemian, just in time before installation, arm
   `scripts/collect-device-pstore --target gemini@192.168.1.50 --wait-for-cycle --wait-seconds 900`.
   It must record the initial boot ID before the installer's shutdown.
2. Run the reviewed installer. It must resolve exactly one live-GPT boot2,
   prove it inactive and unmounted, require the exact rejected predecessor,
   record its checksum without a fresh backup, write only the exact successor,
   verify a matching full-partition readback, remove temporary state, sync the
   deployment evidence, and shut the device down cleanly without reboot.
3. While the device is off, arm the read-only phase USB/netcat collector and
   physically select boot2 once. The inherited expected visible behavior is a
   bounded automatic watchdog restart into ordinary Gemian.
4. After recovery, require changed boot-ID continuity, watchdog-class recovery,
   the known-good Gemian root, CPUs 8/9 offline, inactive and unmounted boot2,
   and unchanged full boot2 checksum
   `2268e23559e8d36e4339a4fd912d0108721ed818e628dfc857cab2ab8e8049a8`.
5. Classify the attributable changed-cycle pstore first. The USB helper emits
   numbered complete log snapshots; its host validator requires exact marker
   occurrence counts, source-valid structure, and monotonic snapshot history.
   It labels an unclosed final envelope as transport-truncated instead of a
   complete prefix. Use USB only as corroboration and never extend the retained
   pstore prefix by assumption.

Decision branches
-----------------

PASS
  Require the complete valid 39-record phase trace, run-exit before terminal,
  an adjacent complete pair-v6 pass and exact pair-v7 pass, no fatal marker,
  changed-cycle watchdog recovery, CPUs 8/9 offline after recovery, and exact
  unchanged boot2. One exact repeat is then earned. Do not enable CPU_OFF.

  The exact pair-v7 success contract is:

    gemini-a72-pair-v7 result=pass parent_pass=1
    sc_reported=1 sc_iterations=262144 sc_rescheds=64
    sc_expected8=8 sc_start8=8 sc_end8=8
    sc_expected9=9 sc_start9=9 sc_end9=9
    sc_task8=1 sc_task9=1 sc_create8=0 sc_create9=0
    sc_wake8 and sc_wake9 must each be 0 or 1
    sc_readywait8=1 sc_readywait9=1
    sc_startwait8=1 sc_startwait9=1
    sc_wait8=1 sc_wait9=1
    sc_error8=0 sc_error9=0 sc_stop8=0 sc_stop9=0
    sc_done8=262144 sc_done9=262144 sc_ready=2 sc_finished=2
    sc_hash8=f678147669874ecd sc_hash9=c2274327e9c8104c

FIRST UNMATCHED PHASE BOUNDARY
  A retained before record without its matching after record, followed by
  continuous fatal/reset evidence rather than arbitrary capture truncation,
  identifies the operation in progress. Record the last completed parent phase
  and both concurrently open task phases, if any. Reject the artifact unchanged
  and inspect only that bounded operation; never invent one failing CPU.

EXPLICIT PAIR-V7 FAULT
  A complete pair-v7 fault terminal is classified by its exact create, wake,
  ready, start, done, task-context, CPU, error, stop, count, and hash fields.
  Reject unchanged and use the earliest attributable source/phase boundary
  corroborated by the complete field vector. If several fields fail without a
  retained ordering boundary, report all co-failing fields and do not invent a
  single cause or CPU. Do not override the vector from screen or reboot
  behavior.

INHERITED PAIR-V6 REGRESSION
  Any pair-v6 value outside its exact pass contract is a parent regression. Do
  not evaluate scheduler success or repeat unchanged.

RUN-EXIT OR TERMINAL-PUBLICATION BOUNDARY
  Run-exit without the adjacent pair terminals localizes the failure after
  task cleanup and before or during terminal publication only when continuous
  fatal/reset evidence follows and rules out capture truncation. Otherwise use
  ATTRIBUTABLE RESTART WITH INCOMPLETE TRACE. A terminal before run-exit
  violates the source contract. Reject unchanged in either established case.

MARKER CONTRACT VIOLATION
  An unknown phase or CPU, duplicate source-instance record, reversed parent or
  per-CPU task order, task phase without CPU, parent phase with CPU, impossible
  source-invariant order, impossible success-claimed cross-causal order, or a
  claimed complete trace with fewer than 39 records invalidates phase
  inference. Preserve the evidence, reject the capture as a classifier input,
  and do not repeat solely from that malformed trace. A missing trace head is
  not by itself a contract violation.

ATTRIBUTABLE RESTART WITH INCOMPLETE TRACE
  Changed-cycle pstore that is continuous from create8-before may end on a
  valid marker prefix without a continuous fatal tail or matching after
  record. Record only the retained prefix. Do not infer the next phase and do
  not repeat unchanged unless a new independent observation path can
  distinguish truncation from terminal-not-reached.

NO ATTRIBUTABLE MARKER OR EVIDENCE LOSS
  A changed cycle with no phase record cannot localize the scheduler fault.
  A trace whose first retained phase is not create8-before is head-truncated
  evidence and also cannot localize the phase from missing history alone.
  Preserve its valid suffix, then separate evidence loss from pre-marker
  failure using console continuity, inherited terminals if present, boot
  reason, and recovery state. Do not reuse a prior visual screen-color report
  as kernel evidence.

LOST RECOVERY OR SAFETY FAILURE
  Missing automatic restart, wrong recovery identity, changed boot2, online
  recovery CPU8/9, unexpected heat, storage errors, or any undeclared fault is
  a safety failure. Recover through known-good Gemian, preserve pstore, verify
  boot2 identity, and do not repeat unchanged.

Success boundary
----------------

One pass establishes only bounded phase attribution plus the inherited
two-thread readiness, authorized release, task-context execution, completion,
and cleanup oracle. A second exact pass establishes repeatability. Neither
result authorizes CPU_OFF, removes the HPS veto, proves production scheduling,
load, thermal, OPP/cpufreq, suspend, or makes CPUs 8/9 production-online.
