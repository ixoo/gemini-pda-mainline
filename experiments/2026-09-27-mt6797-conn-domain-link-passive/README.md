# Passive CONSYS-to-CONN domain association

The [passive provider boot](../2026-09-27-mt6797-conn-provider-passive/results/runtime-1.json) registered exactly one modern CONN domain from an initially OFF state. The shared CONSYS manager still had no association with that domain, so it could not query the provider's retained fault or checked-OFF status through a stable handle.

The named `mt6797-a53-conn-domain-link-passive` profile adds one logical patch. The manager parses a dedicated CONN-domain phandle after acquiring its existing reserve, regulator, reset and remap handles. It uses `of_genpd_add_device()`, which the pinned 7.1.3 source shows does not request `genpd_power_on()`, then calls `mtk_pm_domain_confirmed_off()` before declaring the manager bound. The board DT selects only CONN ID 12. Its binding forbids an ordinary `power-domains` property on the manager, because platform-bus attachment would power the island before the manager's probe. The existing provider retains failed-transition state.

The hypothesis for one later guarded boot is that the provider and manager both bind, the manager's new checked-OFF record appears once, and the A53 service regression remains healthy without a CONN transition. The unique observation is the manager's new record in an authenticated complete kernel log, joined to a changed mainline boot ID and post-recovery Gemian ID. If the provider is unavailable, defer and diagnose population order. If the checked-OFF query fails, preserve the log and both SPM status values, and do not bypass the gate. Any power transition or A53 regression rejects the candidate. A passing boot establishes an association and initial-OFF gate only; it cannot admit rail/reset changes, child population, firmware execution or Wi-Fi.

This is an internal diagnostic patch with synthetic non-certifying authorship. It is not an upstream submission. A later owner transition must prove exclusive writer handoff, serialized fault lifetime, explicit quiescence and the still unresolved EMI protection policy before effect-bearing device testing.

## Passive device result

The [runtime receipt](results/runtime-1.json) binds the exact installed 16 MiB image to changed mainline boot ID `4f0f028b…ece6`. The pre-armed watcher saw `0x20ff`, an absent/unclassified interval, and the candidate gadget before the authenticated direct USB route. Exactly one modern CONN provider was bound, and the manager logged one checked-OFF association. The selected provider's initial-OFF registration guard and the manager's explicit `mtk_pm_domain_confirmed_off()` call both completed. The A53 service regression passed, and all 1,845 kernel records (128,185 bytes) were preserved through an explicit log seal. Reviewed recovery reached changed Gemian boot `82f673dc…4fb8`; a separate pinned-key SSH read confirmed `3.18.41+` and `wlan0` carrier 1.

This consumes the passive association test. It proves the selected manager can attach without requesting a probe-time CONN transition and can observe an OFF state at that instant. It does not prove the later state, exclusive ownership, a safe active transition, firmware execution or mainline Wi-Fi. The next code work is an owner-controlled transition with retained-fault handling and the complete firmware executor; the EMI master/overlap question still gates effect-bearing execution.
