# Gemini DA921x, I2C6, and Cortex-A72 boundary

This document records the durable hardware conclusions at the boundary between
MT6797 I2C6, the Gemini's external DA921x-family buck regulator, and the two
Cortex-A72 CPUs. Detailed candidate construction, raw observations, hashes, and
failed branches remain in the linked experiment records.

## Current boundary

| Area | Current conclusion | Confidence | What remains |
| --- | --- | --- | --- |
| I2C6 ownership | The DVFSP handoff can leave I2C6 serviceable without taking away the shared AP-DMA clock from the working I2C5 path. | `observed` | Resume, error recovery, and stress are untested. |
| Native short transfer | The native packed/FIFO path completes the exact one-byte pointer plus one-byte read transaction. | `confirmed` for this exact shape | Arbitrary lengths, plain writes, and other combined-transfer shapes are unproved. |
| Board-control register contract | The named board exposes a stable legacy DA9213/DA9214/DA9215-compatible direct-address tuple at `0x68` and `0x69`. | `confirmed` for one invocation on one unit | This does not uniquely distinguish DA9213, DA9214, and DA9215. |
| Linux regulator driver | The upstream DA9211/A-family probe does not match the observed legacy protocol. No suitable legacy-family provider is active. | `confirmed` mismatch; implementation `missing` | A dedicated legacy-family driver/binding, or a genuinely separated variant, is needed. |
| Cortex-A53 cluster | Logical CPUs 0–7 can remain online together on the current serviceability baseline. | `observed` | Coherency stress, cpufreq, idle, suspend, and thermal validation remain open. |
| Cortex-A72 cluster | Logical CPUs 8 and 9 remain offline by design. Their external rail ownership and complete safe power sequence are not established. | `unknown` | Provider constraints, rollback, resume, firmware coordination, and the full CPU bring-up chain remain open. |

## Exact durable observations

One gated invocation completed 14 of 14 fixed native transfers. Both
passes over secondary address `0x69` returned:

```text
register 0x05 -> 0xd9
register 0x06 -> 0xd0
register 0x47 -> 0xc0
```

Both passes over primary address `0x68` returned:

```text
register 0xd3 -> 0x1f
register 0x5e -> 0x00
register 0xd9 -> 0x46
register 0xda -> 0x46
```

Distinct receive prefills were overwritten. Each transfer used packed length
`0x0101`, auxiliary length zero, the FIFO receive path, a completion interrupt,
and a FIFO count that changed from one to zero. AP-DMA did not run. The
diagnostic counters changed from `0,0,0,0` to `14,0,14,14`; initialization
remained `1,1`, and the temporary retry-policy change was restored. There was
no explicit reset, error reset, fatal signature, or I2C timeout.

CPU0–7 availability, the CPU8/9-offline state, DVFSP handoff, boot identity,
and USB serviceability remained stable across the invocation. This is repeated
evidence inside one invocation on one unit, not cross-boot or cross-unit
repeatability.

## Observation and inference boundary

The directly observed bytes, transaction shape, and preserved serviceability
support a high-confidence inference that this board uses the legacy
DA9213/DA9214/DA9215 control contract. The independent Gemian and binary
evidence specifically favors the documented DA9214 board design, but the
read-only tuple is not a unique silicon identifier.

The diagnostic requested pointer bytes only. It did not issue a register-data
write, change `PAGE_CON`, register a regulator provider, select a voltage,
enable a rail, or request an A72. It is therefore accurate to say that the
diagnostic requested no voltage or enable action. It is not accurate to claim
that the rail was independently measured unchanged.

The read-only board-contract gate is closed. The following are not established:

- general I2C6 correctness across arbitrary messages, failures, reset recovery,
  suspend, or stress;
- page-selection semantics or any two-byte/register-data write;
- which buck output supplies the A72 cluster and who currently owns it;
- voltage selectors, current limits, enable state, constraints, IRQ behavior,
  rollback, or resume behavior;
- safe provider registration with the existing firmware state;
- the synchronized Gemian CPU8 transaction;
- the complete SRAM-LDO, SPM, clock, CCI, coherency, and firmware sequence;
- CPU8 or CPU9 execution, cpufreq/OPP, idle, suspend, thermal, or scheduling
  policy.

## Implementation decision

Do not make the upstream DA9211/A-family driver emulate the legacy vendor ABI.
The observed chip family, register protocol, transport contract, and resource
model require either:

1. a dedicated DA9213/DA9214/DA9215 legacy-family driver and binding; or
2. a strictly separated legacy variant in an appropriate family driver, with
   no shared probe path that performs A-family identification writes.

The first implementation must use fixed direct addresses and a fail-closed
read-only match. It must not change `PAGE_CON`, write a regulator register,
register a writable consumer path, or request an A72.

The reviewable first-stage software contract is now specified in the
[legacy-family driver design](../../experiments/2026-07-29-da921x-legacy-driver-contract/DESIGN.md).
It is an identification-only boundary with an exact 14-transfer probe and
zero-transaction cleanup, unbind, shutdown, suspend, and resume paths. It does
not change the implementation or hardware-support state recorded above.

## Safety invariants

The authoritative ordered sequence is the
[roadmap](../ROADMAP.md#ordered-gates). This hardware boundary constrains every
step without prescribing their order:

- profiles rejected by the active profile-series audit are not valid
  foundations;
- require fixed-address, fail-closed matching and zero probe-time
  register-data writes;
- keep all regulator consumers and CPUs 8–9 disconnected until their explicit
  gates;
- preserve console, keyboard, USB, CPU0–7, DVFSP, I2C5/AP-DMA ownership, and
  reboot at every hardware step;
- no bounded write is permitted without established ownership, a no-op,
  readback, rollback, and resume behavior; and
- treat CPU8, CPU9, coherency, OPP/cpufreq, idle, suspend, thermal, and
  scheduler policy as separate acceptance gates.

Any failure before a trustworthy register observation remains an I2C,
ownership, or serviceability failure—not regulator or A72 evidence.
