# Hardware support matrix

This is the concise current support view for the Gemini PDA mainline effort.
Detailed investigation narratives, candidate identities, hashes, raw samples,
and rejected branches belong in [`experiments/`](../experiments/README.md).
Durable hardware facts belong in [`docs/hardware/`](hardware/README.md).

Last reviewed: **2026-10-06** for the Bluetooth and RTC/power rows; other rows as of 2026-09-04.

Unless a row says otherwise, runtime evidence applies to the named development
Gemini PDA unit and the local Linux 7.1.3 integration series. A successful
diagnostic profile is not automatically support in the manifest's default
`full` profile or in released upstream Linux.

## State definitions

Runtime state:

| State | Meaning |
| --- | --- |
| `unknown` | No reproducible current-mainline result is recorded. |
| `enumerates` | A driver probes or the device is visible, but function is not established. |
| `partial` | Some intended behavior works, with documented gaps. |
| `working` | The named acceptance test passes on identified hardware and kernel inputs. |
| `stable` | Released upstream code passes a documented regression protocol. |
| `regressed` | A previously passing protocol now fails. |
| `not-applicable` | The hardware is absent on this variant. |

Upstream state:

| State | Meaning |
| --- | --- |
| `missing` | Required support is not known upstream. |
| `local` | A temporary local implementation or board description exists. |
| `RFC` | A public request-for-comments series exists. |
| `submitted` | A patch series is under formal upstream review. |
| `accepted` | A maintainer tree contains the change. |
| `released` | A tagged upstream kernel contains the change. |

Firmware boundary:

| State | Meaning |
| --- | --- |
| `none` | No separately loaded firmware is known for this function. |
| `required-free` | Redistributable firmware is required. |
| `required-nonfree` | Non-redistributable device firmware is required. |
| `unknown` | The firmware or licensing boundary is not established. |

Its guarded standard disconnect was refused by the host interval; second-lifetime key retirement and reconnect remain unproved. Sustained throughput was later measured against the vendor driver on the same host and access point. The vendor figures (14.6/31.5, later 45.1/38.5) were taken on a different BSSID at 5805 MHz and 40 MHz, against mainline's 20 MHz link at 5200 MHz, so they are not a like-for-like driver comparison ([HIF §59](../experiments/2026-10-13-mt6797-wifi-native-delivery-probe/HIF_TRANSPORT_ANALYSIS.md#59-the-vendor-comparisons-are-not-width-matched-2026-10-26)). At the time, mainline reached about 0.88 Mbit/s transmit and 7.1 Mbit/s receive. The receive path is therefore usable and the transmit path is not yet; the measured limit is a host-side per-frame cost plus a fixed 6 Mbps transmit rate, both documented in the [throughput series](../experiments/2026-10-13-mt6797-wifi-native-delivery-probe/THROUGHPUT_SERIES_RESULT.md). With WMM QoS data, HT MCS7 in both directions, receive batching and a depth-12 transmit pump, mainline later reached about 22.6 Mbit/s transmit and 20.5 Mbit/s receive aggregate at best (boots AA3 and AA4; typical band 17.9–22.6 and 15.4–20.5 over the clean runs), the ceiling at 20 MHz without aggregation, since superseded by the 40 MHz result below. The receive engine is a poll: the WLAN HIF interrupt line did not assert in any run, even with every legal WHIER source armed and an enabled source set ([HIF analysis §42](../experiments/2026-10-13-mt6797-wifi-native-delivery-probe/HIF_TRANSPORT_ANALYSIS.md#42-boot-aa6-predeclared-2026-10-26-the-mask-taken-out-of-the-unknowns)). Writing WHIER with the vendor's default before the firmware download, as `nicInitializeAdapter()` does, did not change that either: the value survived to the data phase and the line still never asserted. The interrupt line is closed for this configuration, and the receive engine is polled by design, with the enhanced status block read gated on WHISR: a zero word skips the block, which removed 84 % of the per-pass HIF receive time with no stall ([boot AJ2](../experiments/2026-10-13-mt6797-wifi-native-delivery-probe/HIF_TRANSPORT_ANALYSIS.md#boot-aj2-result-2026-10-26-1906-utc-the-peek-skips-97--of-passes-and-cuts-the-hif-receive-time-per-pass-by-84--the-rates-do-not-move-57s-fourth-row)) ([HIF analysis §45](../experiments/2026-10-13-mt6797-wifi-native-delivery-probe/HIF_TRANSPORT_ANALYSIS.md#boot-aa8-result-2026-10-26-1149-utc-the-vendors-order-changes-nothing-the-interrupt-line-is-closed-for-this-configuration)). [Lifecycle boot 9](../experiments/2026-10-13-mt6797-wifi-native-delivery-probe/LIFECYCLE_RESULT.md) then ran two complete WPA2-PSK station lifetimes on one boot: after the first lifetime's standard disconnect, three-stage cleanup and key removal, the driver re-armed, rescanned, rejoined with fresh keys, ran a second measured data phase (TX 2.5–2.9, RX 5.5–7.1 Mbit/s with two chunks per direction) and tore down again, all in one complete sealed log that the lifecycle classifier passes. That re-arm barrier is host-side (the stage-3 cleanup, the whole ledger retired, both key removals credited), not a firmware guarantee: the firmware's key-done event carries no generation and a returned page credit does not bound event delivery (the event arrives 1–5 ms after the credit), so a stale untagged key event could satisfy a new install window; the PN epochs bound that to a failed lifetime rather than a plaintext leak, and no replay or attribution safety is claimed. At 40 MHz it lost at 0.83×: it settles on MCS7 there with 86 % of frames on their first attempt, against the fixed rate's 95–100 %. That is a rate-control tuning question, not an enablement failure: retry cost and air time are not in its model. The access point's own choice of MCS5–7 at 40 MHz (boot AM) points the same way. Fixed MCS5 at a 40 MHz association is therefore the configuration. A 20 MHz association is worse even with rate control (about 26/31 against 30/38 Mbit/s), and rate control remains available per join. ## Updating the matrix

Keep each row to the current conclusion and remaining gaps. Do not add
candidate-by-candidate chronology here.

Every runtime promotion must link to an experiment record containing:

- exact device variant;
- kernel commit and selected patch/profile revision;
- resolved configuration and toolchain;
- test protocol and repetition count;
- sanitized evidence;
- known negative space;
- upstream series or commit when upstream state changes.

Use `working` only for a named acceptance test. Use `stable` only when released
upstream code passes the project's documented regression protocol.
